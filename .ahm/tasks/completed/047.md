# Ctrl-C during first run loses session pin; next prompt starts fresh instead of resuming

## Summary

When a user cancels an in-flight task with Ctrl-C, the REPL does not pin the next prompt to the session that was already started. On a fresh start (no -resume), the first run begins with --continue/--fresh and receives a TaskStart with a session id. If the user interrupts before TaskComplete, finishRun appends 'canceled' but never updates the session state machine. The next prompt therefore reuses the initial RunFresh/RunContinue mode and creates a new cake session instead of resuming the interrupted one. This breaks the session-hijack prevention intent and can split a conversation across two sessions.

## Fix Direction

Add a cancellation path to the session state machine so that an interrupted run still pins the next prompt to the session that was started. The cleanest place is in `internal/app/session.go` with a new method such as `OnCancel()` that, if a `SessionID` is known, transitions `NextMode` to `cake.RunResume` and `ResumeID` to that session id. If no session id was reported yet, the state should fall back to the previous `RunOptions` behavior (typically `RunContinue` or `RunFresh`) so the next prompt does not invent a session id.

Call this method from `internal/app/update.go` `finishRun` when `res.Canceled` is true, before appending the "canceled" timeline item. Update `internal/app/session_test.go` to cover:

- Fresh start → TaskStart with session id → cancel → next run resumes the same session.
- Resume start → cancel → next run still resumes the same explicit session.
- Cancel before TaskStart → state remains usable (does not create a phantom session).
