# Reconcile cancellation classification with its documented invariant

**Code-review finding (2026-07-19).** High confidence on the doc/code
contradiction; the practical race window is narrow.

## Problem

ARCHITECTURE.md:76-79 and both guardrail docs
(`docs/guardrails/session-and-security.md` "Cancellation races",
`docs/guardrails/cake-integration-and-stream-json.md` "Mislabeling
cancellation") state that cancellation is "classified from `Wait`'s error, not
from the context directly, so a late Ctrl+C cannot relabel a finished run."

The `ExitError` branch does exactly what the docs forbid:

```go
case errors.As(waitErr, &exitErr):
    res.ExitCode = exitErr.ExitCode()
    res.Canceled = ctx.Err() != nil   // internal/cake/runner.go:236
```

If cake exits non-zero on its own and a Ctrl+C lands between stdout EOF and
this classification, the failed run is relabeled "canceled": the exit code and
stderr tail are hidden (`finishRun` takes the `res.Canceled` branch,
`internal/app/update.go:443-457`) and `OnCancel` runs instead of the failure
path.

The ctx check cannot simply be deleted: when the user cancels and cake dies
from SIGTERM/SIGKILL, `Wait` also returns an `ExitError`, and the ctx check is
what labels that as a cancel. The invariant as documented is not fully
achievable from `Wait`'s error alone.

## Relevant Files

### To modify
- `internal/cake/runner.go` — classification in the `Start` goroutine.
- `ARCHITECTURE.md`, `docs/guardrails/session-and-security.md`,
  `docs/guardrails/cake-integration-and-stream-json.md` — restate the
  invariant to match what the code actually guarantees.

### Tests
- `internal/cake/runner_test.go` — fake-cake script that exits non-zero, with
  `Cancel()` called after the stream ends; assert the result is a failure, not
  a cancel.

## Fix Direction

Record whether cancellation was requested *before* the process exited — e.g.
an atomic flag set inside `cmd.Cancel` (which exec only invokes while the
process is still running), and classify the `ExitError` branch from that flag
instead of `ctx.Err()`. Then a Ctrl+C after exit can no longer relabel the
run, and the docs become accurate as written.

Minimum viable alternative: keep the code and fix the three doc locations to
say the guarantee only covers the clean-exit path.

## Decision (grooming 2026-07-21)

Implement the cancellation-request flag described above; do not weaken the
documented invariant. Set the concurrency-safe flag from `cmd.Cancel` before
signaling the process, and use it only when classifying an `ExitError`.
Continue to classify `context.Canceled` from `Wait` as canceled. The regression
test must deterministically arrange a non-zero process exit before calling
`Cancel`, rather than relying on timing sleeps.

**Preflight refinement (2026-07-23).** A successful POSIX signal does not prove
the process was still running because an exited-but-unreaped zombie can accept
the signal. In the `ExitError` branch, require both the cancellation-request
flag and signal-terminated process status; retain the flag-only path on Windows,
where `Kill` does not expose POSIX wait status. This preserves SIGTERM/SIGKILL
cancellation while keeping natural non-zero exits on the failure path.

## Documentation / ADR Notes

- User docs: no change required; this fixes an internal race without changing
  the intended terminal behavior.
- Architecture and guardrails: retain the existing invariant and clarify the
  flag-based ordering where useful in `ARCHITECTURE.md` and both named
  guardrails.
- ADR: not required because the implementation is being corrected to satisfy
  an already-documented subprocess invariant.
