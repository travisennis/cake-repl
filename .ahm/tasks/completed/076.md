# Pin the next prompt to --resume when a task fails after announcing a session id

## Problem

A cake task that fails after announcing a session id leaves the REPL unable to
reach that session again. `sessionState.OnTaskComplete`
(`internal/app/session.go:31`) only advances the run mode when
`!e.IsError`, so a failure on the first prompt of a REPL leaves `NextMode` at
`RunFresh` — and the next prompt starts a brand-new session, orphaning
everything the failed run accomplished.

Observed 2026-08-09: a cake session ran 90 turns and 111 tool calls over ~11
minutes, then died on a provider-side 400. The follow-up prompt "try again"
spawned a fresh session with zero prior context instead of resuming the 420-record
session file cake had already written, including its failing `task_complete`.

## Why the current behavior is wrong

ADR 001 states the rule as "a failed task does not advance the run mode … this
prevents a failed run from accidentally causing a mode switch into a state the
user didn't request." That reasoning targets the `RunContinue` fallback — the
actual hijack vector — but it also blocks the safe `RunResume` transition.

`OnCancel` (`internal/app/session.go:54`) already handles the identical
situation correctly: an interrupted run pins to `RunResume` when a session id
was announced, "so the next submission does not accidentally start a new one."
A `task_complete` with `is_error: true` has the same shape as a cancel — cake
has written a complete, resumable session file either way. The two paths should
agree.

## Direction

Make the error path of `OnTaskComplete` mirror `OnCancel`: when `SessionID` is
non-empty, pin `NextMode` to `RunResume` with `ResumeID = SessionID`. When no
session id was ever announced, leave the run mode untouched — do **not** fall
back to `RunContinue` on failure, since that is the hijack vector ADR 001
exists to close.

Keep `sessionState` pure and I/O-free.

## Documentation impact

- `docs/adr/001-session-run-mode-pinned-to-resume-to-prevent-hijack.md` states
  the failure rule in "Decision Outcome"; it needs to record the new rule and
  why the cancel and failure paths converge.
- `docs/guardrails/session-and-security.md` lists "A failed task must not
  advance the run mode" as a compatibility surface and "advancing run mode on a
  failed task" as a hijack failure mode; both need restating around the
  continue-versus-resume distinction.
- `ARCHITECTURE.md` invariants mention the run-mode transitions.
- `README.md` / `HelpText` only if user-visible session behavior is described
  there.

## Acceptance

- A failed task that announced a session id pins the next prompt to
  `--resume <id>`.
- A failed task that never announced a session id does not advance the run
  mode and never selects `RunContinue`.
- `/new`, `/resume`, and `/continue` overrides still win.
- `session_test.go` covers both failure branches; the existing
  failure-does-not-advance case is updated rather than deleted.
- `just ci` passes.
