# Render the prompt input as a focused composer

## Summary

Make the prompt input feel like the active place to work by rendering it as a focused composer instead of an unframed textarea between a rule and the status bar. Today the input is functional but visually reads like another block of terminal output, which makes the REPL feel utilitarian and harder to scan. The composer should clarify where to type, expose the most important submit/newline/help hints, and preserve the existing multiline textarea behavior.

Written against commit `a9b0ced`.

Depends on task `042` so the prompt can use shared semantic theme roles instead of introducing isolated styles.

## Evidence

- `internal/app/model.go:81` — the textarea is configured with a long placeholder and no line numbers, then focused; there is no custom prompt-specific visual treatment.
- `internal/app/view.go:16` — the view renders `timeline`, a faint full-width rule, `m.input.View()`, and `statusLine()` directly, so the active input has no title, border, hint row, or focus affordance.
- `internal/app/model.go:241` — layout sizes the raw textarea based on line count, but there is no accounting for prompt chrome such as borders or hint rows.
- `README.md` keybinding docs and `internal/app/commands.go` `HelpText` list the input controls; the in-app composer should surface only the most useful hints without changing the bindings.

## Fix Direction

Add a pure rendering helper in `internal/ui` for the prompt composer, then have `internal/app.View` pass the rendered textarea, width, running/idle state, line count, and concise hint text into it. Keep `textarea.Model` as the input engine unless there is a strong reason to stop and document a different design. Update layout constants and calculations in `internal/app/model.go` so the viewport height accounts for any composer border/title/hint lines without overlap or clipping. Do not change submit semantics, slash-command parsing, prompt history, completion, session behavior, or the cake subprocess contract.
