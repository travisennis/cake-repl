# Bound timeline memory: the transcript is retained several times over

**Code-review finding (2026-07-28).** Sibling of task 054 — same hot path, but
this is the memory axis rather than the latency axis.

## Problem

A running REPL holds the whole transcript roughly four times:

1. `m.items` — the structured items, including **full untruncated tool output**.
   `applyEvent` stores `e.Output` verbatim (`internal/app/update.go:390`);
   `outputLimit` is applied only at render time
   (`internal/ui/timeline.go:139-153`), so a 50 MB command result is retained in
   full to display 2 KB of it.
2. `m.rendered` — one styled string per item, typically larger than the source
   because of ANSI sequences and padding.
3. `m.timelineContent` — a full concatenation of `m.rendered`
   (`internal/app/model.go:333-342`).
4. The Bubble viewport's own copy, split into lines by `SetContent`.

`MaxTimelineItems` defaults to 0, meaning unbounded
(`cmd/cake-repl/main.go:124`), so nothing caps any of this during a long
session with chatty tools.

There is a second-order effect worth noting: because `internal/cake`'s event
channel is only 64-buffered (`internal/cake/runner.go:206`), once per-event
work gets slow the REPL stops draining, cake's stdout pipe fills, and the
engine itself stalls. Memory pressure and the task 054 latency problem
therefore reinforce each other.

## Relevant Files

### To modify
- `internal/app/update.go` — the `FunctionCallOutput` branch that stores raw
  output.
- `internal/app/model.go` — `appendItem`, the `rendered`/`timelineContent`
  cache, `trimFront`.
- `internal/ui/timeline.go`, `internal/ui/toolblock.go` — `TruncateOutput` and
  the Ctrl+O full-output mode, which is the constraint on retaining raw bytes.

### Tests / verification
- `internal/app/model_test.go`, `internal/ui/toolblock_test.go`.
- `internal/app/model_bench_test.go` with `-benchmem` — allocation and
  retention deltas belong in the same instrument task 054 uses.

## Fix Direction

Sequence this **after** task 054, which is already restructuring the same cache;
doing both at once will conflict.

Candidate levers, cheapest first:

1. **Cap retained tool output at ingest.** The tension is Ctrl+O
   (`ToolOutputFull`), which exists precisely to show untruncated output. A
   generous hard ceiling well above `output-limit` — retaining, say, the first N
   MB and marking the remainder dropped — keeps Ctrl+O useful for realistic
   output while removing the unbounded case. Pick N deliberately and document
   it; do not silently reuse `output-limit`.
2. **Reconsider the `MaxTimelineItems` default.** Task 054 explicitly defers
   this as a product decision; it belongs here. An unbounded default is the
   reason none of the other bounds bind.
3. **Stop holding three copies of the rendered form.** Whatever structure task
   054 lands on for `timelineContent` should not coexist with a separate
   `rendered` slice *and* a viewport copy if one can be derived cheaply.

Measure before and after: the point is retained bytes for a realistic session,
not micro-allocations.

## Acceptance criteria

- [x] A single tool result of arbitrary size no longer pins its full bytes for
      the life of the session; the cap is documented and Ctrl+O behavior for
      normal-sized output is unchanged.
- [x] Timeline memory for a long session is bounded by a stated policy, and the
      `MaxTimelineItems` default is either changed or its unbounded default is
      recorded as deliberate.
- [x] Retained-bytes measurements for a representative session are recorded
      before and after.
- [x] `/clear` and Ctrl+N actually release the memory they appear to.

## Implemented (2026-08-27)

All four acceptance criteria are met; the unbounded `MaxTimelineItems` default
was **kept deliberately** (recorded in ADR 010, not changed). Task 054 already
removed the persistent `timelineContent` string (lever 3 is satisfied: the
`rendered` slice is joined lazily and only the viewport keeps a second
retained copy, which is Bubble internals), so this task did the remaining
levers:

1. **Ingest cap on retained tool output** (`internal/app/update.go`): at most
   `maxRetainedToolOutputBytes` (1 MiB) of any single tool result is kept,
   rune-safe, cut via `ui.TruncateOutput` so the standard "… truncated (N
   bytes total)" marker explains the drop. Applied at both `FunctionCallOutput`
   write sites (in-place and orphan). Below the ceiling, output is retained
   verbatim, so `Ctrl+O` full mode is unchanged for realistic output. The raw
   stream still goes to the debug log in full (runner writes before decode).
2. **Release on clear / new-session / trim** (`internal/app/model.go`):
   `rebuildTimeline` drops the render cache's backing array when the timeline
   is empty (`/clear`, `Ctrl+N`); `trimFront` and the `appendItem` render trim
   copy survivors into fresh slices so `-max-timeline-items` trimming actually
   releases the trimmed payloads instead of keeping them reachable behind a
   resliced header.
3. **Deliberate unbounded default** (ADR 010 + `README.md`): per-entry
   retention is now bounded (tool output ≤ 1 MiB; rendered forms ≤
   `-output-limit`), so the count default stays unlimited rather than silently
   dropping scroll-back history.

### Measured Evidence (before/after, Apple M5, darwin/arm64, `-count=6`)

Instrument: `BenchmarkTimelineRetainedMemory` in
`internal/app/model_bench_test.go` — deterministic wire sum of retained item
payloads + render cache, no GC involved. Environment as above; command:
`go test -run '^$' -bench 'BenchmarkTimelineRetainedMemory' -benchmem -count=6
./internal/app/`.

| Case | before (retained-B) | after (retained-B) |
| --- | --- | --- |
| normal-tools (200 items) | 456,600 | 456,600 (unchanged) |
| + one 50 MiB tool result | 52,887,869 (~50.4 MiB) | 1,507,682 (~1.4 MiB) |

A 50 MiB command result dropped from ~50 MiB to ~1.4 MiB retained (~97%
fewer bytes). The oversized setup also runs ~2.6× faster (Sanitize no longer
scans the full 50 MiB). No hot-path regression: alloc counts on the
`BenchmarkTimelineToolOutputEndToEnd` / burst family are identical to before
(the cap adds zero allocations for output under the ceiling — a `len` check).

### Notes / decisions

- The 1 MiB ceiling is a constant, not a flag — CLI/config surfaces unchanged.
- `ToolBlock.Arguments` is not capped (out of scope: the task is about tool
  *results*; capping args would misreport write-tool byte counts). Noted as a
  follow-up if large write/read args ever show up in practice.
- The second-order effect from the 64-buffered event channel (`runner.go:206`)
  is a latency concern owned by task 054; not touched here.
