# Tool output wrapping for names and arguments

## Problem

Tool output blocks show the tool name and its arguments in the header, but long tool names (especially Bash commands) get truncated instead of wrapping. This makes it difficult to see the full command that was executed, which is critical for Bash tools where the command is the most important piece of information.

Current rendering (in `internal/ui/toolblock.go`) applies width constraints that truncate rather than wrap the tool name and argument display.

## Proposed solution

Make the tool name and argument display wrap (word-wrap or line-wrap) within the available width so the full command is always visible. This may involve:

- Changing width-constrained rendering to allow wrapping in the tool header
- Adjusting any fixed-height assumptions in the tool block rendering
- Ensuring wrapped content respects indentation

Out of scope: changing tool output content truncation (that's task 010 / 005).

## Relevant files

- `internal/ui/toolblock.go` — `renderTool`, tool name/args rendering
- `internal/ui/timeline.go` — tool block dimensions
- `internal/app/update.go` — tool event handling

## Acceptance Notes

Implementation (`internal/ui/toolblock.go`, `internal/ui/timeline.go`):

- Added `renderToolHeader`, which renders the `⚙ <name>` prefix plus the first
  line of the argument summary, wrapping the summary to fit the terminal width
  with continuation lines indented under the argument column. Each wrapped
  line is styled independently so lipgloss does not pad the block to its
  longest line (which previously pushed the prefix past the width).
- Added `wrapToolArgs`: a greedy, whitespace-only word wrap that does **not**
  break at hyphens (so CLI flags like `--no-pager` stay intact), with a
  hard-wrap fallback for oversized single tokens (long paths/commands) so no
  content is lost. Wrapping is cell-aware via `lipgloss.Width`. Continuation
  indent is capped at narrow widths so there is always room for content.
- `summarizeBash` no longer pre-clips the command to 200 cells
  (`firstLineOf(cmd, 200)` → `firstLineNoLimit(cmd)`); the full first line is
  returned so the render layer can wrap it. The multiline-command `…` marker
  is preserved.
- Added `firstLineOnly` / `firstLineNoLimit` helpers; `firstLineOf` is still
  used by `summarizeEdit` previews.

Out of scope (per task): tool *output* content truncation (tasks 010/005) is
unchanged — `TruncateOutput` still caps output at the configured limit.

Docs: `docs/guardrails/cli-and-user-output.md` updated under "Output rendering"
to describe header wrapping vs. output truncation. README not changed: it never
described header rendering, and the tool-output truncation line in "Known
limitations" remains accurate for output only. No CLI flags, config, slash
commands, key bindings, persisted state, or subprocess behavior changed, so no
ADR is required (UI rendering polish, not a durable architectural decision).
