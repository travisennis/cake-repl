# Gate CI on unreachable functions with the Go deadcode tool

## Problem

An exported function that nothing calls is invisible to this repository's gate.
`just lint` enables `unused` (staticcheck), which reports unexported dead code
only: exported identifiers are assumed to be a package's contract. Every
package here is under `internal/`, so nothing outside this module can import
them, and the assumption is wrong for this codebase.

Two independent preflight sessions, reviewing an unrelated diff, each checked
`.golangci.yml` for exactly this and each concluded the gate cannot catch an
uncalled exported helper. The only thing that noticed was a human reading the
call-site search.

## Evidence (measured 2026-09-22; Go 1.27.1, golangci-lint v2.13.1)

Scratch module using this repository's linter set from `.golangci.yml`, with an
`internal/thing` package holding one unused exported and one unused unexported
function:

- `golangci-lint run` → `func unexported is unused (unused)`. Silent on
  `Exported` and on `LegacyKind`.
- `go run golang.org/x/tools/cmd/deadcode@latest ./...` →
  `unreachable func: Exported`, `unreachable func: LegacyKind`,
  `unreachable func: unexported`.

On this repository and a clone of it:

- `deadcode ./...` and `deadcode -test ./...` → zero findings, so adopting the
  gate needs no cleanup pass.
- With a planted exported helper: `internal/ui/theme.go:73:6: unreachable func:
  DeadProbe` and `unreachable func: deadUnused`.

Measured limits:

- Functions and methods only. A planted unused exported `type DeadType`, `var
  DeadVar`, and `const DeadConst` were all unreported.
- `-test` is required. Without it, a helper called only from a `_test.go` file
  is reported unreachable — a false positive; with `-test` it is kept alive.
- No suppression mechanism exists, so a false positive (typically a method
  reached only through reflection or across a module boundary) would need a
  root-side reference rather than an inline ignore.

## Direction

Pin the tool the way `govulncheck` is pinned, then make it part of the gate:

```makefile
deadcode_version := "v0.50.0"
```

- `install-tools` / `install-tools-ci`: add
  `go install golang.org/x/tools/cmd/deadcode@{{ deadcode_version }}`.
- New recipe: `deadcode: deadcode -test ./...` (the `-test` flag is not
  optional).
- `ci:` gains `deadcode` in the existing chain.

`deadcode` is a dev tool, not a runtime dependency: no `go.mod` change, and per
the documentation impact matrix no ADR is required. The pinned versions must
stay consistent across the `justfile`, `CONTRIBUTING.md`, and
[the dependencies/release guardrail](../../../docs/guardrails/dependencies-build-ci-release.md),
and `just ci` is enumerated in more than one document — sweep every
enumeration, not just the `justfile`.

Do not add it to `.pre-commit-config.yaml`: the hook set is scoped to fast,
per-commit checks (fmt, tidy, test, lint) and `deadcode` builds a whole-program
call graph. `just ci` is the right home.

## Acceptance criteria

- [x] `golangci_lint_version`-style pin `deadcode_version` exists in the
      `justfile` and both `install-tools` recipes install it.
- [x] `just deadcode` runs `deadcode -test ./...` and exits non-zero on a
      finding.
- [x] `deadcode` is part of `just ci`, and every document that enumerates the
      `just ci` steps lists it.
- [x] `CONTRIBUTING.md` documents the recipe and, in the project-specific
      pitfalls, says what the lint gate cannot see and why this tool exists.
- [x] `docs/guardrails/dependencies-build-ci-release.md` lists `deadcode` with
      its pinned version alongside the other tools.
- [x] `docs/guardrails/testing-and-verification.md` names it in the ladder or
      its compatibility surface.
- [x] Negative check recorded: a planted uncalled exported function fails
      `just deadcode` (and `just ci`), then is removed.
- [x] `just ci` green on the final tree.

## Constraints

- Never run this check as a warning-only step; a gate that cannot fail is not a
  gate.
- Keep the Go MSRV and pinned tool versions consistent across `go.mod`, the
  `justfile`, docs, and CI.
- Do not weaken an existing linter to make the new one look cleaner.
- The tool reports the class of defect, not a judgement about intent: an
  exported API that is intentionally ahead of its caller is still a finding
  here, and the answer is to land the caller or not land the API. Record that
  as the policy in `CONTRIBUTING.md` so the first finding is not a surprise.

## Verification

- `just deadcode` clean on the repository.
- Plant `func DeadProbe() string { return "" }` in `internal/ui/theme.go`,

- `just ci` green, including the new step.
- In CI, confirm the workflow installs the pinned tool and that a planted dead

## Acceptance Notes (2026-09-22)

Implemented as specified; verified locally end to end.

- Pin: `deadcode_version := "v0.50.0"` in the `justfile`, installed by both
  `install-tools` and `install-tools-ci`. The installed binary reports
  `mod golang.org/x/tools v0.50.0`.
- **The raw tool exits 0 even when it reports findings** (confirmed in
  `x/tools@v0.50.0/cmd/deadcode/deadcode.go` and by experiment), so the recipe
  converts findings into a failure itself. It is a `#!/bin/sh` recipe:
  `just deadcode` prints 0 bytes and exits 0 on a clean tree, and prints the
  finding plus guidance and exits 1 on a planted one.
- Negative check run twice: planting `internal/ui/deadprobe.go` with an
  uncalled exported `DeadProbe` made `just deadcode` exit 1 and `just ci` exit
  1; deleting the file returned both to exit 0.
- `just ci` green on the final tree, including the new step.
- Enumeration sweep: only three places list the `just ci` steps
  (`justfile`, `CONTRIBUTING.md`, `testing-and-verification.md`) and they agree.
  No workflow edit was needed: `ci.yml` and `release.yml` each call
  `just install-tools-ci`, which now installs the pinned binary, and the
  justfile puts `tool_dir` on `PATH` for every recipe.
- Deliberately not added to `.pre-commit-config.yaml`: that hook set is the fast
  subset (fmt-check, tidy-check, test, lint), and vet, vuln, build, and
  release-check are equally absent.

Preflight (one M-scale pass; lenses: build/toolchain and instruction/doc
surfaces) reported two wording defects in lines this change wrote. Both applied:

- `CONTRIBUTING.md` over-promised `-test`: a helper whose only caller is in an
  `integration`-tagged test is still reported, and this repository has such a
  file. The caveat is documented; the alternative (`-tags=integration` in the
  recipe) would change which build the gate analyzes and was deliberately not
  taken.
- The dependencies guardrail said deadcode is installed "only through
  `install-tools`" and that its version is referenced by the workflows. Both are
  wrong for the CI path; reworded to name both install recipes and the absent
  workflow `version:` field.

Deferred: the CI-side confirmation. A green `ci.yml` run (proving
`install-tools-ci` installs the binary) cannot happen until this is pushed, so
that check is recorded here rather than run.

Known limits carried from the task body: functions and methods only (not types,
vars, or consts); no suppression mechanism, so a reflection-reached symbol would
need a root-side reference; code behind non-default build tags is invisible to
the default analysis.
