# Improve timeline visual grouping and scan hierarchy

## Summary

Improve the readability of the conversation timeline by adding clearer visual grouping for user prompts, assistant replies, reasoning summaries, tool calls, status events, warnings, and errors. Recent work improved markdown rendering and tool-header wrapping, but the timeline still relies mostly on glyphs and simple color differences, so dense sessions can be hard to scan. The goal is better hierarchy and spacing without changing the stream-json schema or event handling.

Written against commit `a9b0ced`.

Depends on task `042` so timeline grouping can reuse shared semantic theme roles.

## Evidence

- `internal/ui/timeline.go:57` — `RenderItem` switches on item kind and renders most kinds as a glyph plus styled text; there is little structural grouping or metadata hierarchy.
- `internal/app/model.go:217` — timeline items are joined with a fixed double newline, so spacing is uniform across assistant messages, tool calls, warnings, errors, and small status events.
- `internal/ui/timeline.go:68` — user prompts render as `❯ ` plus faint text, making the user's submitted prompt lower contrast than many operational events.
- `internal/ui/timeline.go:93` — tool blocks are grouped internally, but they are not visually differentiated as collapsible/secondary operational material beyond the tool header and faint output.

## Fix Direction

Refine `internal/ui.RenderItem` and related helpers so each timeline item kind has an intentional role: user prompts should be recognizable anchors, assistant messages should remain readable markdown, reasoning and tool output should feel secondary, and warnings/errors/completions should be easy to spot. Consider left gutters, labels, subtle separators, indentation, or kind-specific spacing, but keep rendering string-based and side-effect-free. Preserve the timeline render cache contract in `internal/app/model.go`; do not bypass cached per-item rendering or change when width rebuilds happen. Do not alter event parsing, item kind semantics, tool-output truncation, or the cake stream-json contract.
