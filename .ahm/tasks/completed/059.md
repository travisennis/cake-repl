# Benchmark timeline event hot-path costs

## Purpose

Measure the costs identified by task 054 before selecting an implementation.
The benchmark must distinguish new-item rendering, cached timeline string
maintenance, and Bubble viewport content ingestion so the follow-up fix targets
the dominant cost instead of optimizing one layer speculatively.

## Relationship to task 054

This task is a prerequisite for task 054. It performs measurement and records a
design recommendation; it does not implement the production optimization.
After the results are recorded, revise task 054 with the smallest design that
measurably addresses the dominant cost and make 054 ready for acceptance.

- `internal/app/model.go`

## Work plan

1. Add reproducible Go benchmarks with increasing timeline sizes. Include
   representative small, medium, and long sessions and report allocations as
   well as elapsed time.
2. Separate the following costs so results are attributable:
   - rendering one newly appended timeline item;
   - extending `timelineContent` on the append path and rebuilding it for an
     in-place item update, without viewport synchronization;
   - calling `viewport.SetContent` with already-rendered content;
   - the end-to-end append path;
   - the end-to-end `FunctionCallOutput` update path.
3. Cover both append-only traffic and tool-call/output traffic. Use stable,
   realistic payloads, fixed terminal dimensions, deterministic fixture data,
   and explicit size sub-benchmarks.
4. Run the focused benchmarks multiple times with `benchstat` when available,
   or preserve the raw repeated runs when it is not. Record the environment,
   exact commands, timeline sizes, `ns/op`, and allocation results.
5. Interpret growth per event as the timeline expands. Identify which layer
   dominates and whether task 054's roughly-flat goal is attainable through
   app-side string changes alone.
6. Update task 054 with the measurements, the selected smallest viable design,
   expected verification, and any documented Bubble viewport limitation. Keep
   production optimization work in task 054.

## Acceptance Notes

### What was added

`internal/app/model_bench_test.go` — six benchmarks over two workloads
(`text` = user/assistant/reasoning traffic, `tools` = completed tool blocks)
at three timeline sizes (50, 200, 800), all hermetic (no `cake` binary, fixed
100x30 terminal, fixed payloads):

| Benchmark | Layer measured |
| --- | --- |
| `BenchmarkTimelineRenderItem` | `ui.RenderItem` for one new item, no cache or viewport |
| `BenchmarkTimelineAppendContent` | `appendTimelineContent` only (`+=` on the cached string) |
| `BenchmarkTimelineRebuildContent` | `rebuildTimelineContent` only (`strings.Join`) |
| `BenchmarkTimelineViewportSetContent` | `viewport.SetContent` on already-rendered content |
| `BenchmarkTimelineAppendEndToEnd` | `appendItem`: render + cache + `syncViewport` |
| `BenchmarkTimelineToolOutputEndToEnd` | `applyEvent(FunctionCallOutput)`: in-place mutation + `rerenderItem` |

Design notes for future readers:

- Per-iteration state reset is O(1) (string header assignment, slice reslice),
  so no `b.StopTimer` is needed and the timeline size stays fixed inside each
  sub-benchmark. `viewport.SetContent` is never hidden in setup.
- The end-to-end append benchmark pre-grows `items`/`rendered` capacity so the
  loop does not pay one slice growth per iteration; production amortizes that
  growth across many appends.
- Benchmarks force `termenv.TrueColor` via `lipgloss.SetColorProfile` and
  restore it on cleanup. Without a TTY lipgloss would strip every escape
  sequence and hide the ANSI-parsing work `viewport.SetContent` performs on
  real terminal output.
- The item appended or rendered in the measurement loop is fixed per workload
  (`benchWorkload.newItem`), not derived from the timeline size. Deriving it
  from the size silently measured a single kind, because every entry in
  `benchSizes` lands on the same point in the filler cycle. Text traffic
  measures the assistant markdown reply — the most expensive kind — so the
  per-event denominator is honest. Per-kind `ui.RenderItem` cost for reference:
  user ≈ 12µs / 54 allocs, reasoning ≈ 3.9µs / 28 allocs, assistant ≈ 221µs /
  1822 allocs, tool ≈ 21µs / 138 allocs.

### Interpretation

- **`viewport.SetContent` is the dominant cost that grows with the session, and
  it is the whole source of the O(n²) behavior.** At 800 items it is 83% of the
  end-to-end append on both workloads. It scales almost perfectly linearly:
  ×3.95 then ×3.97 (text) and ×4.20 then ×3.93 (tools) for each ×4 in size.
  Cumulative session cost is therefore O(n²), as task 054 claims — but the
  constant belongs to the viewport, not to the string concatenation.
- **App-side string maintenance is small.** `appendTimelineContent` is 4.6%
  (text) and 6.2% (tools) of the end-to-end append at 800 items, and 2.5–7.0%
  at the smaller sizes. `rebuildTimelineContent` is 3.1% (text) and 3.3%
  (tools) of the end-to-end tool-output update at 800 items. Task 054's
  original lever is confirmed to be the wrong one.
- **Rendering is flat in n but is a large fixed floor for text traffic.** An
  assistant markdown item costs 221µs and 1822 allocations — more than
  `SetContent` for timelines below roughly 120 items, and still 12% of the
  per-event cost at 800. A tool item costs 21µs; cheap kinds (user 12µs,
  reasoning 3.9µs) are negligible. Glamour is the cost, and it does not shrink
  with any change to the timeline string or the sync frequency.
- **Both workloads agree on the layer attribution.** `AppendEndToEnd` ≈
  `RenderItem` + `AppendContent` + `SetContent` (text/800: 1.802m predicted vs
  1.810m measured) and `ToolOutputEndToEnd` ≈ tool `RenderItem` +
  `RebuildContent` + `SetContent` (text/800: 1.567m predicted vs 1.562m
  measured), confirming the layers are additive and the attribution is sound.
  The tools workload runs ~10% above the sum, which is GC pressure from its
  larger payloads.
- **Why `SetContent` costs what it does** (bubbles v1.0.0
  `viewport/viewport.go:125-133`): it normalizes line endings, re-splits the
  entire payload with `strings.Split`, then calls `findLongestLineWidth`
  (`viewport.go:536-544`), which runs `ansi.StringWidth` over *every* line.
  That is a full ANSI parse of the whole timeline on every event. Its single
  allocation is small (only the `[]string` headers) but its CPU cost is
  proportional to total rendered bytes.
- **Consequence for task 054**: its acceptance criterion "per-event cost
  roughly flat as the timeline grows" is **not attainable through app-side
  string changes alone**. Replacing `+=` with a `strings.Builder` or a
  `[]string` of lines removes at most ~6% of the per-event cost at 800 items
  while `SetContent` keeps the path linear. The lever that measurably matters
  is reducing *how often* `SetContent` runs, not what it is handed.
- After coalescing K events into one sync, the remaining per-batch cost is
  K×(render + string) + one `SetContent`. At 800 items with K=10 that makes
  string maintenance ~18% (text) / ~40% (tools) of a batch — the right *second*
  step for tool traffic. For text traffic the larger remaining term is markdown
  rendering (~49% of the batch), which no timeline-string change addresses.
- `MaxTimelineItems` already bounds n and therefore bounds the per-event cost;
  it defaults to unbounded, so long sessions grow without limit.
