# Hydrate resumed sessions from cake replay support

## Problem
`cake-repl -resume <uuid>` currently pins the next prompt to an existing cake session, but the TUI starts with an empty local timeline. Users reasonably expect a resumed session window to show prior conversation history before they continue.

Today cake-repl has not integrated the supported replay path. It must still preserve the engine boundary: it must not read cake session files, parse cake's human output, or import cake internals.

## External dependency status

The external blocker is resolved. Cake 0.1.0 supports the documented
`cake --output-format stream-json replay <uuid>` command. Cake's replay ADR and
integration contract define a read-only transcript stream, additive metadata
records, and structured non-zero failures.

The supported contract is:

- `cake --output-format stream-json replay <uuid>` emits replay events for an
  existing session without running a new prompt.
- The replay stream preserves record order and includes user and assistant
  messages, reasoning summaries when available, tool calls, tool outputs, task
  boundaries, session and task ids, and completion metadata.
- Replay uses the live `stream-json` vocabulary plus additive
  `session_meta`, `prompt_context`, and `skill_activated` records. It omits the
  session-only `turn_usage` record.
- Replay failures emit a structured `replay_error` record and exit non-zero:
  input errors use exit 3; corrupt, unsupported-format, and permission errors
  use exit 1.

Do not implement this by reading `~/.local/share/cake/sessions/*.jsonl` directly from cake-repl.

## Fix Direction
Once cake provides a supported replay/export contract:

1. Add a cake integration path that invokes the replay/export command for the selected resume id before the first prompt runs.
2. Decode replay records through the same event parser when possible. If cake adds replay-specific event types, add them forward-compatibly in `internal/cake/events.go`.
3. Hydrate the timeline during model initialization or early `Init` without marking a live prompt as running.
4. Preserve current session pinning behavior: after hydration, the next submitted prompt still uses `--resume <uuid>`.
5. Show a clear, non-fatal timeline warning when replay fails, then still allow the user to continue with `--resume <uuid>`.
6. Update user-facing docs so `-resume` explicitly says it reloads visible history when cake replay support is available.

## Implementation Notes

- Added `cake.Replay` with the exact `cake --output-format stream-json replay
  <uuid>` invocation and shared runner lifecycle.
- Added typed replay metadata/errors and provider-compatible reasoning summary
  decoding through the existing forward-compatible parser.
- Startup resume hydration runs through Bubble Tea `Init` in a separate state;
  replayed user messages and ordered transcript events populate the timeline,
  while failures warn and preserve the explicit resume pin.
- Replayed dangling tool calls are marked complete with the existing task-ended
  marker so partial transcripts do not appear to run forever.
