# Decide whether -debug-log and -history-file should refuse symlinks

**Code-review finding (2026-07-28).** Low severity; may be a deliberate
won't-fix. Left Open.

## Problem

Both user-supplied file paths are opened with `O_CREATE` and mode `0600` but
follow symlinks:

- `cmd/cake-repl/main.go:215` — `-debug-log`, which receives raw cake stream
  content.
- `internal/app/update.go:311` — `-history-file`, which receives every prompt
  the user submits.

If either path is a pre-existing symlink, the write lands at the link target,
with the mode applying only to a file that had to be created. Both files carry
sensitive content by design — the debug log deliberately holds raw stream data,
and prompts routinely contain private context — so redirecting them is a real,
if narrow, information disclosure.

The attack requires an attacker who can already plant a symlink at a path the
user then passes explicitly on the command line, which is a weak position; this
is a hardening question, not an urgent defect. The relevant guardrail
(`docs/guardrails/session-and-security.md`) does commit to owner-only writes for
the debug log, and following a symlink to a location with different ownership
does not honor that commitment in spirit.

## Relevant Files

- `cmd/cake-repl/main.go` — the `-debug-log` open.
- `internal/app/update.go` — `persistHistory`.
- `internal/app/model.go` — `loadHistory`, which also opens a user-supplied
  path.
- `docs/guardrails/session-and-security.md` — states the owner-only write rule.

## Fix Direction

If taken: use `O_NOFOLLOW` on the final component when creating, or `Lstat`
first and refuse when the path is a symlink, reporting a clear startup error for
`-debug-log` and a silent skip (matching current best-effort semantics) for
history. Note `O_NOFOLLOW` behavior differs across platforms; a `Lstat` check is
more portable but has a TOCTOU gap, so pick one and state the tradeoff.

Weigh it against a legitimate use: pointing `-debug-log` at a symlink into a
scratch directory is a reasonable thing for a user to do deliberately. A hard
refusal may be more annoying than the risk warrants — which is why this is a
decision rather than a straightforward fix.

If not taken, record that here and close the task.

## Decision (2026-08-01)

Accept symlinks — won't fix, closed. Both `-debug-log` and `-history-file`
continue to follow symlinks. The attack requires an attacker who can already
plant a symlink at a path the user explicitly passes, and symlinked targets
(for example a scratch directory) are a legitimate use. Recorded tradeoff: the
session-and-security guardrail's owner-only claim applies at file creation —
`OpenFile(..., 0o600)` does not narrow an existing file's permissions — so the
claim should be reworded to "at creation" when the guardrail is next edited.

## Acceptance criteria

- [ ] A decision is recorded: refuse symlinks, or accept them with reasoning.
- [ ] If refused, both paths behave consistently and the error is actionable.
- [ ] The debug-log guardrail's owner-only claim matches actual behavior.
