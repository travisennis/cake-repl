# Fix multi-line prompt corruption in the persisted history round-trip

**Code-review finding (2026-07-19), high confidence.** Enter inserts a newline
(Ctrl+S submits), so multi-line prompts are the normal case — and they corrupt
the `-history-file` round-trip.

## Problem

`persistHistory` appends the raw prompt text plus `"\n"`
(`internal/app/update.go:288-300`), embedding real newlines in the file.
`loadHistory` reads the file line-by-line with `bufio.Scanner` and treats each
line as one entry (`internal/app/model.go:126-155`).

Consequences:

- A 5-line prompt becomes 5 unrelated history entries on the next start.
- The `maxHistoryEntries` cap and the rewrite-on-load trim count *lines*, not
  prompts.
- Up-arrow recall after restart returns fragments of prompts.

In-memory history within one session is unaffected; only persistence is broken.

## Relevant Files

### To modify
- `internal/app/update.go` — `persistHistory`: encode entries so one entry is
  one record.
- `internal/app/model.go` — `loadHistory`: decode the same encoding.

### Tests
- `internal/app/history_io_test.go` — round-trip a multi-line prompt through
  persist + load; assert one entry comes back byte-identical.

## Fix Direction

Pick one encoding; escape-based keeps the file line-oriented and mostly
backward compatible with existing single-line entries:

- On write: escape `\` → `\\` and newline → `\n` (two characters).
- On read: reverse the escaping per line.

Alternatives: NUL-delimited records, or JSON lines. Whatever is chosen,
existing plain single-line history files should still load.

## Acceptance criteria

- [ ] A multi-line prompt persisted to the history file loads back as a single
      entry with newlines intact.
- [ ] Existing single-line history files still load unchanged.
- [ ] `maxHistoryEntries` trimming counts entries, not physical lines.
- [ ] `go test ./...` passes.
