# Consider a ceiling on single-line reads from the cake stream

**Code-review finding (2026-07-28).** Low severity; may be a deliberate
won't-fix. Left Open.

## Problem

The stdout reader has no upper bound on line length
(`internal/cake/runner.go:216-229`):

```go
reader := bufio.NewReader(stdout)
for {
    line, readErr := reader.ReadString('\n')
```

This is intentional — the comment explains that `bufio.Scanner` was rejected
because long tool outputs must not abort the stream, which is the right call.
The consequence is that a single record is read fully into memory, then copied
again into the decoded event (and, for unknown types, a third time — see the
`Unknown.Raw` task), and mirrored to the debug log if one is configured
(`internal/cake/runner.go:220-222`).

A malformed or runaway cake — one emitting a record with no newline, or a
single enormous tool result — can therefore drive memory with no backstop. cake
is trusted, and its stdout is not attacker-controlled in the usual sense, so
this is a robustness ceiling rather than a vulnerability.

## Why it might be worth doing anyway

The failure mode is silent and terminal: the REPL grows until the OS kills it,
with no timeline message explaining why. A bounded reader could instead surface
"stream line exceeded N MB" as a `ParseError`-style event and keep the session
alive, which matches how the package already handles every other malformed
input.

## Relevant Files

- `internal/cake/runner.go` — the read loop.
- `internal/cake/events.go` — if a new synthetic event type is warranted, or
  reuse `ParseError`.
- `internal/cake/runner_test.go`, `internal/cake/parser_integration_test.go`.

## Fix Direction

If taken: read with an explicit cap (a `io.LimitedReader` per line, or manual
accumulation with a ceiling), emit a synthetic error event when a line exceeds
it, and skip forward to the next newline so the stream keeps flowing — the same
resilience contract `ParseError` already provides.

Choose the ceiling with the real workload in mind: tool outputs of several MB on
one line are plausible, so the cap should be generous enough to never fire in
normal use.

If not taken, record that decision here and close the task, so the next review
does not re-raise it.

## Acceptance criteria

- [ ] A decision is recorded: bounded, or deliberately unbounded with reasoning.
- [ ] If bounded, an oversized line produces a visible timeline warning and the
      stream continues rather than the process dying.
- [ ] Normal long tool output is unaffected.
- [ ] The existing comment explaining why `bufio.Scanner` was rejected stays
      accurate.
