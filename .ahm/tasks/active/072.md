# Expand tabs to real tab stops in ui.Sanitize

Follow-up to task 061 and
[ADR 005](../../../docs/adr/005-untrusted-stream-content-is-sanitized-at-the-ui-render-boundary.md).

## Problem

`ui.Sanitize` (`internal/ui/sanitize.go`) replaces every tab with a fixed
four-space run. That was chosen for simplicity while closing the terminal
injection hole; it is not the best available behavior, and it trades one
defect for another.

Before task 061, raw tabs reached the terminal, which advanced the cursor to
the next 8-column tab stop, while `lipgloss.Width("\t")` measured them as 0
(verified). Alignment looked right; the wrapping and padding math was wrong.

After task 061, the width math is honest but column alignment is wrong:
tab-separated output (`go test` output, `column -t`, `df`, `docker ps`,
hand-made ASCII tables in tool output) no longer lines up, because a fixed
four-space run is not a tab stop.

Both defects are avoidable. Expanding to real tab stops gets honest width
*and* correct alignment.

## Relevant Files

### To modify
- `internal/ui/sanitize.go` — `Sanitize` and the `sanitizeTab` constant.

### Tests
- `internal/ui/sanitize_test.go` — direct unit cases.
- `internal/ui/sanitize_render_test.go` — the width/alignment render cases.

## Fix Direction

Track the output column while scanning and pad each tab to the next multiple
of the tab width, resetting the column at each `\n`:

```go
col := 0
// on '\t': pad := tabWidth - col%tabWidth; write pad spaces; col += pad
// on '\n': col = 0
// otherwise: col += rune width
```

Notes and decisions to make:

- Use 8 columns, the terminal default, unless there is a reason to prefer 4.
- Count *cells*, not runes: wide runes (CJK, emoji) advance two columns, so
  use `ansi.StringWidth` semantics rather than a rune counter, or the tab
  stops drift on non-ASCII lines.
- `x/ansi` v0.11.6 has no tab-expansion helper (checked: only cursor/DECTABSR
  helpers), so this is local code.
- The column origin is the sanitized string's own column 0, not the terminal's.
  Tool output is later indented by two cells and wrapped by lipgloss, so stops
  are relative to the block, not the screen. That is the same approximation any
  pager makes; note it in the code rather than trying to thread a real origin
  through `RenderItem`.

## Acceptance criteria

- [ ] Tabs expand to the next tab stop, not a fixed-width run.
- [ ] Column tracking resets on `\n`.
- [ ] Tab stops stay correct on lines containing wide (CJK/emoji) runes.
- [ ] Width math stays honest: no rendered line exceeds the requested width,
      and the existing task 061 width tests still pass.
- [ ] Tab-separated tool output visibly aligns in a manual check.
- [ ] ADR 005's "Bad, because tabs render as fixed four-space runs" consequence
      and the README known-limitation wording are updated to match.
- [ ] `docs/guardrails/cli-and-user-output.md` no longer says "tabs expand to
      four spaces".
