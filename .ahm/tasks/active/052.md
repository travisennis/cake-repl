# Fix Tab-completion cycling (second Tab resets instead of advancing)

**Known bug, documented in the test suite** (`internal/app/tabcomplete_test.go:8-15`
and `TestHandleTabCompleteSecondTabReset`). Re-confirmed during code review
(2026-07-19).

## Problem

`handleTabComplete` decides whether the user edited the input since the last
Tab by comparing the current input against the original `completionPrefix`
(`internal/app/update.go:170-175`). But after the first Tab the input holds
`matches[0]`, not the prefix, so the second Tab always matches the "input
changed" condition and resets the cycle. The advance/wrap branch at
`internal/app/update.go:206-220` is effectively unreachable.

Example: `/q` → Tab → `/quit` (cycle starts, matches `[/quit /q]`) → Tab →
reset, fresh completion on `/quit` → single match → stuck on `/quit`. `/q` is
never reachable by cycling; same for `/c` (`/continue` vs `/clear`) and the
bare-`/` all-commands cycle.

## Relevant Files

### To modify
- `internal/app/update.go` — `handleTabComplete`.

### Tests
- `internal/app/tabcomplete_test.go` — replace
  `TestHandleTabCompleteSecondTabReset` (which asserts the buggy behavior) with
  advance and wrap-around tests, per its own comment.

## Fix Direction

Track the value the completer itself last set (e.g. a `completionLast` field,
or compare against `completionMatches[completionIdx]`). Reset the cycle only
when the input differs from *that* value; otherwise advance:

- Tab on `/q` → `/quit` (idx 0)
- Tab → `/q` (idx 1)
- Tab → restore prefix `/q`, end cycle (existing wrap behavior)
- Typing anything (handled in `handleKey`, which already clears the state) or
  editing the input still starts a fresh cycle.

## Acceptance criteria

- [ ] Repeated Tab cycles through every match and wraps to the original

- [ ] Editing the input mid-cycle still resets and completes fresh.

      replaced with advance/wrap coverage.
