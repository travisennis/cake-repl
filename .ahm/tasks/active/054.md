# Reduce O(n^2) timeline content maintenance on the event hot path

**Code-review finding (2026-07-19).** High confidence on the mechanism; impact
grows with session length, so profile before restructuring heavily.

## Problem

Every appended event pays a cost proportional to the *entire* timeline:

- `appendTimelineContent` does `m.timelineContent += rendered`
  (`internal/app/model.go:333-338`). Go string `+=` copies the whole
  accumulated string, so the append path is O(total bytes) — the comment on
  the cache ("so appends do not join the full rendered slice on the hot
  path", `internal/app/model.go:76-81`) claims a saving that string
  concatenation does not deliver.
- `rerenderItem` — hit on every `FunctionCallOutput` — calls
  `rebuildTimelineContent`, a full `strings.Join` (`internal/app/model.go:340-342`).
- `syncViewport` → `viewport.SetContent` re-splits the full content into lines
  on every update (`internal/app/model.go:347-356`).

With the default unbounded timeline and a chatty stream, cumulative cost is
O(n²) over a session; long sessions with heavy tool output will feel it.

## Measured Evidence (task 059, 2026-07-27)

Full numbers, environment, and method are in `.ahm/tasks/*/059.md`. The
headline, at 800 timeline items on an M5:

| Layer | text traffic | tool traffic |
| --- | --- | --- |
| Render one new item | 220.9µs (flat in n) | 21.3µs (flat in n) |
| `appendTimelineContent` (`+=`) | 83.7µs | 112µs |
| `rebuildTimelineContent` (`Join`) | 48.9µs | 57.1µs |
| **`viewport.SetContent`** | **1.497ms** | **1.502ms** |
| End-to-end append | 1.810ms | 1.818ms |
| End-to-end tool-output update | 1.562ms | 1.745ms |

- `viewport.SetContent` is **83% of the per-event cost at 800 items** on both
  workloads and scales linearly (×3.95/×3.97 text, ×4.20/×3.93 tools, per ×4
  timeline size). It is the only layer that grows with n, so it is the entire
  source of the O(n²) session cost.
- All app-side string maintenance is **4.6–6.2%** of the per-event cost at 800
  items.
- Rendering the new item is flat in n but is not negligible for text traffic: an
  assistant markdown item costs 220.9µs and 1822 allocations (glamour), which
  exceeds `SetContent` below roughly 120 timeline items. Batching syncs does not
  reduce it.
- Cause (bubbles v1.0.0 `viewport/viewport.go:125-133`): `SetContent`
  re-splits the whole payload and then runs `ansi.StringWidth` over every line
  via `findLongestLineWidth` (`viewport.go:536-544`) — a full ANSI parse of the
  entire timeline on every event.
- **Therefore the original plan is wrong about the lever.** Replacing `+=`
  with a `strings.Builder` or a `[]string` of lines removes at most ~6% of the
  per-event cost, and the path stays linear in n either way.

## Fix Direction (selected)

Smallest design that measurably attacks the dominant cost — reduce *how often*
`SetContent` runs, not what it is handed:

1. **Fix the misleading comment** on the `rendered`/`timelineContent` fields
   (`internal/app/model.go:76-81`). Correct regardless of any perf work.
2. **Coalesce viewport syncs across an event burst.** `waitForRun` delivers one
   event per `Update`, so a burst of K events pays K full `SetContent` calls.
   Drain the already-available events from `run.Events` non-blockingly into one
   batch message (the channel is buffered at 64 in
   `internal/cake/runner.go:206`, so a burst really does queue), apply them in
   order, and call `syncViewport` once at the end
   (e.g. a `timelineDirty` flag set by `appendItem`/`rerenderItem`/
   `rebuildTimeline` and cleared by a single sync per `Update`). This divides
   the dominant cost by the burst factor with no change to rendering,
   ordering, or the cake contract.
   - Preserve: `newSessionPending` suppression, the `runDoneMsg` transition on
     channel close, and spinner responsiveness (bound the batch so one Update
     cannot starve the event loop).
3. **Then, and only then, fix the string path.** Once syncs are amortized, a
   batch of K=10 events at 800 items spends ~40% (tool traffic) or ~18% (text
   traffic) of its time on string maintenance, so switching the append path to
   a `strings.Builder` (or a `[]string` of lines) becomes a measurable win
   instead of noise. Note that for text traffic the largest remaining term is
   then markdown rendering (~49% of the batch), which is out of scope here.
4. **Do not** try to make per-event cost flat by re-setting content only when
   the changed item is visible: the viewport needs the whole payload to compute
   `maxYOffset`, and bottom-pinned is the common case. True flatness requires
   replacing the Bubble viewport with a line-buffer that appends — a larger
   change that belongs in its own task (and interacts with task 060).

Do not regress: width-change rebuilds, `/clear`, Ctrl+O tool re-renders, and
scroll-position preservation in `syncViewport`.

`MaxTimelineItems` already bounds n and therefore bounds the per-event cost. It
defaults to unbounded; whether to change that default is a separate product
decision, not part of this task.
