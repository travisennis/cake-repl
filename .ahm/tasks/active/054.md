# Reduce O(n²) timeline content maintenance on the event hot path

**Code-review finding (2026-07-19).** High confidence on the mechanism; impact
grows with session length, so profile before restructuring heavily.

## Problem

Every appended event pays a cost proportional to the *entire* timeline:

- `appendTimelineContent` does `m.timelineContent += rendered`
  (`internal/app/model.go:301-306`). Go string `+=` copies the whole
  accumulated string, so the append path is O(total bytes) — the comment on
  the cache ("so appends do not join the full rendered slice on the hot
  path", `internal/app/model.go:75-79`) claims a saving that string
  concatenation does not deliver.
- `rerenderItem` — hit on every `FunctionCallOutput` — calls
  `rebuildTimelineContent`, a full `strings.Join` (`internal/app/model.go:262-269`).
- `syncViewport` → `viewport.SetContent` re-splits the full content into lines
  on every update (`internal/app/model.go:315-324`).

With the default unbounded timeline and a chatty stream, cumulative cost is
O(n²) over a session; long sessions with heavy tool output will feel it.

## Relevant Files

### To modify
- `internal/app/model.go` — `appendTimelineContent`,
  `rebuildTimelineContent`, `rerenderItem`, `syncViewport`, and the cache
  comment on the `rendered`/`timelineContent` fields.

### Tests / verification
- Existing render-cache tests in `internal/app/model_test.go` must keep
  passing.
- Add a benchmark (`go test -bench`) appending N items and delivering N tool
  outputs to quantify before/after.

## Fix Direction

Incremental options, cheapest first:

1. Fix the misleading comment regardless of any perf work.
2. Keep a running line-count offset per item and maintain the viewport
   content as a `[]string` of lines (or use `strings.Builder` for the pure
   append path) so appends stop copying the whole timeline.
3. The hard ceiling is `viewport.SetContent`'s full-content model; if
   measurement shows it dominating, consider only re-setting content when
   visible (item within or near the viewport window) or debouncing syncs
   during event bursts.

Do not regress: width-change rebuilds, `/clear`, Ctrl+O tool re-renders, and
scroll-position preservation in `syncViewport`.

## Next Action (grooming 2026-07-21)

Keep this task Open until a benchmark separates three costs: rendering the new
item, extending/rebuilding `timelineContent`, and `viewport.SetContent`.
Record results for increasing timeline sizes and both append-only and tool
output update workloads. Then revise this task with the smallest selected
design that measurably improves the dominant cost. Do not accept the task on a
speculative `strings.Builder` change: `SetContent` still processes the full
payload, so that alone cannot satisfy the roughly-flat acceptance criterion.

## Acceptance criteria

- [ ] The `rendered`/`timelineContent` field comment matches reality.
