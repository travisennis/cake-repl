# Add explicit "Things That Deliberately Do Not Exist" section to ARCHITECTURE.md

**Based on `docs` audit finding** — `architecture_codemap` scored 2/3 because ARCHITECTURE.md documents invariants but does not call out things that deliberately do not exist in a dedicated section.

## Problem

ARCHITECTURE.md currently documents six architectural invariants. Several of these imply absences (e.g., "Engine isolation" implies "cake-repl never links to cake internals"), but they are framed as rules rather than as deliberate design absences. The most valuable information a new contributor gains from an architecture doc is often *what is NOT there* — the things an experienced developer from a similar project would expect to find but this project deliberately avoids.

Without an explicit "Things That Deliberately Do Not Exist" section, agents and contributors waste time:
- Looking for integration code with cake internals (it deliberately does not exist).
- Looking for a database or persistent state layer (the app has none).
- Looking for a web server or API layer (the REPL is a terminal app only).
- Looking for a plugin system, feature flags, or dynamic config reload.

## Relevant Files

### To modify
- `ARCHITECTURE.md` — add a new section with the absences list.

### Read-only context
- The existing invariants section — overlaps should be merged or cross-referenced.
- `internal/app/model.go`, `internal/cake/runner.go` — to confirm absences are real (no hidden persistence, no network calls).

## Grooming Decision (2026-07-03)

**Place as a standalone section between the Module Map and Architectural Invariants.**

The proposed absences list is about half overlapping with existing invariants. This is intentional — invariants are prescriptive rules ("always do X"), while absences are descriptive ("there is no Y"). Some overlap between the two is fine and even clarifying. A standalone section keeps the distinction clear and makes both easier to scan.

If the absences section grows long in the future, it can be merged into the invariants section with a "What does not exist" subsection. Not needed now.

## Fix Direction

Add a new section to `ARCHITECTURE.md`, placed between the Module Map and Architectural Invariants, as a standalone section:

```markdown
## Things that deliberately do not exist

- **No linking to cake internals.** The only contract with cake is its CLI and
  NDJSON stream output. See the system boundary section above.
- **No persistent state machine.** Session state is a pure in-memory struct
  (`session.go`) and is not persisted by cake-repl. Prompt history and the
  optional exit-session summary are separate file surfaces, not a serialized
  application state machine.
- **No database.** The REPL does not use a database. Prompt history is stored
  in a line-oriented file. Configuration is read from TOML at startup.
- **No web server or network calls.** cake-repl is a local terminal application.
  All network activity (LLM API calls) is handled by the external cake process.
- **No dynamic config reload.** Config is read once at startup. Changing the
  config file while the REPL is running has no effect.
- **No plugin system.** All behavior is compiled into a single binary. There is
  no hook or plugin interface.
- **No cake output parsing beyond NDJSON.** The REPL never reads cake's standard
  text output, session files, or log files.
- **No concurrent cake processes.** The REPL allows at most one cake subprocess
  at a time. Submitting while a task runs is rejected.
```

Alternatively, if this list overlaps heavily with the existing invariants, add the section as a prefix to the invariants with a brief note: "The invariants above represent prescriptive rules; the list below captures what does not exist by design."

### Acceptance criteria

- [ ] ARCHITECTURE.md has an explicit "Things That Deliberately Do Not Exist" section (or equivalent heading).
- [ ] Each absence is concrete, not a restatement of an invariant in negative form.
- [ ] No absence on the list is contradicted by the codebase.
- [ ] The section is concise (~10–15 items max) — it documents absences, not everything the project does.
- [ ] Internal links to ARCHITECTURE.md for references like "See ARCHITECTURE.md" still resolve.

## Constraints

- Do not expand ARCHITECTURE.md beyond ~15–20 additional lines for this section.
- Do not remove or rephrase existing invariants — the new section complements them.
- Each absence should be genuinely deliberate, not just absent because the project hasn't gotten there yet (e.g., "no session browser" is a known limitation, not a deliberate absence — keep that in the README; "no database" is a deliberate absence — put it here).
