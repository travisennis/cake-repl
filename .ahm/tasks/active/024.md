# Add integration tests: testdata fixtures, multi-line parser tests, and real-cake smoke test

## Summary

The test suite is solid at the unit level but has no integration, end-to-end, or smoke-test layer. Runner tests already use a subprocess pattern (`writeFakeCake`), but they never exercise the real `cake` binary. There is no `testdata/` directory, and no multi-event stream parsing tests exist. Adding integration tests closes the `validation_harness` gap identified in the agentic-legibility audit (score 2/3 → 3/3).

## Problem

1. **No real-cake smoke test.** The runner test suite spawns fake shell scripts, not the actual `cake` binary. A change in cake's `stream-json` output shape or a bug in the subprocess lifecycle (flag composition, cancellation, stderr handling) won't be caught until a human runs the REPL manually.

2. **Parser tests are single-line only.** Each parser test feeds exactly one JSON line. There is no test that feeds a multi-line NDJSON file through `ParseLine` and verifies the entire event stream in sequence — meaning ordering, interleaving of types, and the forward-compatible `Unknown` handling across a real stream aren't exercised.

3. **No reusable test fixtures.** The `writeFakeCake` helper already embeds inline NDJSON strings in each test function. A `testdata/` directory would let parser tests, runner tests, and any future integration layer share the same stream fixtures rather than repeating them.

4. **No integration-level test for the full pipeline.** From `Start()` → subprocess → `Events` channel → `ParseLine` → typed events, there's no single test that verifies the whole chain works together.

## Relevant Files

### Existing (review before touching)
- `internal/cake/runner_test.go` — fake-cake runner tests (7 tests, `writeFakeCake` helper, `collect` helper). These stay; integration tests go in a separate file.
- `internal/cake/parser_test.go` — single-line parser tests (10 tests). These stay.
- `internal/cake/runner.go` — the `Start()` function, `Options` struct, `Run` struct.
- `internal/cake/events.go` — the event type definitions and the `Event` interface.
- `CONTRIBUTING.md` — states "the test suite does not need a cake binary". This invariant must be preserved: real-cake tests must skip when cake is absent.

- `internal/cake/parser_integration_test.go` — multi-line fixture tests.

### Phase 1: Create `testdata/fixtures/`

Create NDJSON fixture files under `internal/cake/testdata/fixtures/` with one scenario per file:

| File | Scenario | Event count | Notes |
|------|----------|-------------|-------|
| `happy-path.ndjson` | Full success: task_start → message → function_call → function_call_output → task_complete(success) | 5 | Same shape as the inline string in `TestRunnerHappyPath` |
| `error-task.ndjson` | Task that fails: task_start → message → task_complete(error) | 3 | IsError=true, includes error field |
| `minimal.ndjson` | Bare minimum stream: task_start → task_complete(success) | 2 | Tests boundaries |
| `unknown-type.ndjson` | Stream with a future/unknown event type: task_start → {"type":"future_feature",...} → task_complete | 3 | Tests forward compatibility |
| `malformed-midstream.ndjson` | Stream with a non-JSON line between valid events | 3 | Tests ParseError handling across stream |

Each fixture is plain NDJSON, one JSON object per line, no trailing blank lines. All use fixed UUIDs for reproducibility (`11111111-2222-3333-4444-555555555555`, `t-1`).

### Phase 2: Multi-line parser integration tests

Add tests to `internal/cake/parser_integration_test.go`. Each test:

1. Reads a fixture from `testdata/fixtures/<name>.ndjson` with `os.ReadFile`.
2. Splits on `\n`, calls `ParseLine` on each non-empty line.
3. Asserts:
   - Correct number of events.
   - Correct event types in order (use type assertions, not just string matching).
   - Key field values (session ID, content, error flag, etc.).
4. For the `malformed-midstream` fixture, asserts that a `ParseError` event is produced and the stream continues past it.

A helper function `parseFixture(t, name string) []Event` reads and parses a fixture, making individual tests one-liners.

### Phase 3: Real-cake smoke test

Add `internal/cake/runner_integration_test.go`:

```go
// Build tag: keep unit tests fast by default.
//go:build integration
```

Also skip unless `CAKE_REAL_SMOKE=1`, then check `CAKE_BIN`/`PATH`:

```go
func TestSmokeRealCake(t *testing.T) {
    cakeBin := os.Getenv("CAKE_BIN")
    if cakeBin == "" {
        cakeBin = "cake"
    }
    if _, err := exec.LookPath(cakeBin); err != nil {
        t.Skip("cake binary not found; set CAKE_BIN or add cake to PATH")
    }
    // ...
}
```

The test:
1. Spawns `cake --output-format stream-json -- "echo hello"` (a trivial prompt that always succeeds).
2. Drains events and result using the existing `collect` helper.
3. Asserts:
   - At least 2 events (task_start + task_complete).
   - First event is `TaskStart` with non-empty `SessionID` and `TaskID`.
   - Last event is `TaskComplete` with `IsError == false`.
   - `result.ExitCode == 0`, `result.Canceled == false`, `result.Err == nil`.
   - No `ParseError` events.
4. Uses a generous timeout (30s) to accommodate model latency.

Do NOT test against a model that costs money. Use a trivial prompt that cake can answer with zero or minimal tool calls, or test only the flag/stream contract, not the model behavior.

### Phase 4: Full-pipeline integration test

A test in `internal/cake/runner_integration_test.go` that:
1. Uses a fake-cake script to emit a known NDJSON stream.
2. Feeds it through `Start()` → `ParseLine` → typed events.
3. Asserts the full typed event chain matches expectations.
4. This is mostly covered by existing runner tests + new fixture-based parser tests, but a single end-to-end test that verifies the `Start()` output flows correctly through `ParseLine` is valuable as a regression guard.

### Test infrastructure improvements
