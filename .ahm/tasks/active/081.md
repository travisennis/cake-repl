# Add a skill for verifying UI changes by driving the REPL in a PTY

## Problem

`CONTRIBUTING.md` requires "a terminal capture when UI output changes" in a PR,
and [`cli-and-user-output.md`](../../../docs/guardrails/cli-and-user-output.md) says
"For UI/output changes, capture a terminal screenshot for the PR." No document
says how to produce one.

The tests cannot substitute. They call `Update` and `View` directly and assert
on strings; nothing in the suite drives the Bubble Tea program, a real
terminal, or a real cake stream. `cli-and-user-output.md` now records this as a
common failure mode ("Mistaking a green suite for proof that output is
right"), which makes the missing procedure the next gap to close.

Consequence today: a rendering change is verified by the author's memory of a
manual run, or an agent asked to verify one either skips the evidence or spawns
a real cake (cost, nondeterminism, no reproducible screen).

## Why a skill and not more prose in `AGENTS.md`

`AGENTS.md` is a map: it names the surface and routes to the document that owns
the rules. The step-by-step procedure for driving a TUI belongs beside the work
it governs, per the [agent-facing instructions
guardrail](../../../docs/guardrails/agent-instructions.md) ("Keep procedure out of
the map").

## What already exists to build on

- `internal/cake/testdata/fixtures/*.ndjson` — deterministic streams: happy
  path, error task, minimal, unknown type, malformed midstream, replay.
- `writeFakeCake` in `internal/cake/runner_test.go` — writes an executable
  `/bin/sh` script that stands in for cake. Currently inline per test, so it is
  not reusable outside Go tests.
- `-cake-bin <path>` — the flag that lets the real binary run a fake engine.
- `-no-color`, `-cwd`, `-history-file`, `-config`/`-no-config` — the isolation
  levers for a repeatable screen.
- `just run *args` — runs the REPL from source.
- Available on the dev machine (no new dependency needed): `tmux` 3.7c,
  `expect`, `script`.

## Direction

1. Add a checked-in fake cake script (e.g. `scripts/fake-cake.sh`) that replays
   a named fixture from `internal/cake/testdata/fixtures/`, with an optional
   delay between lines so a running state is observable. It must stay hermetic:
   no real cake, no network, no model calls.
2. Add `.agents/skills/drive-tui/SKILL.md` covering: launch the REPL in a named
   background session against the fake cake with fixed `--cols`/`--rows`; wait
   reactively for expected text instead of sleeping; snapshot after every
   action; send text and Enter as separate writes; always pass a timeout;
   tear down only sessions the skill started; capture a text snapshot (and/or
   PNG) as the PR artifact.
3. Name the skill from `cli-and-user-output.md` under "Required checks / test
   focus", so the capture requirement has a documented procedure.

### Open decision (settle during grooming)

Which PTY driver:

- **`tmux`** — already installed, headless, `capture-pane` gives a clean
  screen snapshot, `send-keys` types. Zero new dependencies.
- **`expect`/`script`** — POSIX-ish, but asserting on screen state is clumsier
  than `capture-pane`.
- **An in-repo Go PTY helper** (`creack/pty`) with screen assertions — the
  strongest determinism and it reuses the fixture harness, but it is really a
  test-infrastructure task, not a documentation one.

Recommendation: use `tmux` for the skill now (it unblocks evidence immediately
at zero dependency cost) and treat the Go PTY helper as a separate follow-up if
the manual path proves unreliable. Confirm before implementing.

## Acceptance criteria

- [ ] `.agents/skills/drive-tui/SKILL.md` exists with frontmatter `name` and a
      `description` that states when to use it (rendering, status line,
      composer, key bindings, resize, color) and when not to.
- [ ] The skill launches the REPL against the checked-in fake cake; no step
      needs a real cake or spends money.
- [ ] The skill names the isolation flags (fake cake, `-no-color`, fixed
      cols/rows, temp history and config) so two runs produce the same screen.
- [ ] The skill states the observe → act → observe rule: wait for a predicate,
      snapshot after each action, never `sleep`.
- [ ] The skill says how to produce the PR capture and where to put it.
- [ ] `docs/guardrails/cli-and-user-output.md` "Required checks / test focus"
      names the skill.
- [ ] Under the dependencies/release guardrail's rules, state whether the
      chosen driver is a new dev dependency (tmux: no) and record it.
- [ ] Evidence: a fresh agent session follows the skill and produces a text
      capture of a real UI change without asking questions. Record the session
      in the task before completion.

## Constraints

- No new dependency for the shipped binary.
- Never require a real `cake`; the `integration` + `CAKE_REAL_SMOKE` gating in
  `runner_integration_test.go` stays as it is.
- Sessions are shared with the human: never close a session the skill did not
  start.
- Keep `-no-color` usable in every step, so the procedure works on a bare
  terminal.
- Do not duplicate the guardrail's rule in `AGENTS.md`; routing already reaches
  it.

## Verification

- Run the skill's own steps end to end against the fake cake.
- Re-run once with a different `--cols` value to confirm the procedure is not
  width-dependent.
- Confirm the capture requirement is met for a real change: pick one existing
  UI task (e.g. 073, SGR passthrough) or a trivial local edit and produce the
  artifact the skill prescribes.
