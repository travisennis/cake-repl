# Fix stale pendingCalls indices when -max-timeline-items trims the timeline

**Confirmed with a reproduction test** during a code review (2026-07-19): with
`MaxTimelineItems: 3` and two pending tool calls, one trim caused call A's
output to be written into tool B's block; tool B was marked done with A's
output and tool A stayed "… running".

## Problem

`appendItem` trims the front of `m.items` when over the `MaxTimelineItems` cap
but never adjusts the `pendingCalls` map (`internal/app/model.go:185-199`).
`insertItemAt` handles the identical trim correctly — it deletes trimmed
entries and shifts the surviving indices (`internal/app/model.go:232-247`) —
so the two paths have diverged.

Every append past the cap shifts all items left by `over` while the map keeps
the old indices. Consequences once trimming starts:

- A `FunctionCallOutput` resolves to the wrong index, writing output into a
  *different* pending tool's block (`internal/app/update.go:371-384`).
- The displaced tool never receives its output and renders "… running" until
  `finishRun` walks the same stale indices (`internal/app/update.go:434-441`)
  and marks the wrong items "(no output — task ended)".

## Reproduction

```go
m := New(Config{MaxTimelineItems: 3})
m.width, m.height = 80, 24
m.layout()
m.applyEvent(cake.FunctionCall{CallID: "A", Name: "bash", Arguments: `{"command":"echo a"}`})
m.applyEvent(cake.FunctionCall{CallID: "B", Name: "bash", Arguments: `{"command":"echo b"}`})
m.applyEvent(cake.Reasoning{Summary: []string{"thinking"}}) // len 4 > 3 → trims info item
m.applyEvent(cake.FunctionCallOutput{CallID: "A", Output: "OUTPUT-A"})
// tool B's block now holds OUTPUT-A; tool A is still pending
```

## Relevant Files

### To modify
- `internal/app/model.go` — `appendItem`: apply the same pendingCalls
  delete/shift adjustment `insertItemAt` already does in its trim branch.

### Tests
- `internal/app/update_test.go` or `model_test.go` — add the reproduction
  above as a regression test; also cover a pending call whose item is itself
  trimmed away (entry must be deleted, late output falls back to a standalone
  block).

## Fix Direction

In `appendItem`, after computing `over`, mirror `insertItemAt`:

```go
for callID, callIdx := range m.pendingCalls {
    if callIdx < over {
        delete(m.pendingCalls, callID)
    } else {
        m.pendingCalls[callID] = callIdx - over
    }
}
```

Consider extracting a shared `trimFront(over int)` helper so the two paths
cannot drift again.

## Acceptance criteria

- [ ] The reproduction above passes: A's output lands on tool A, tool B stays
      pending until its own output arrives.
- [ ] A pending call trimmed out of the window is removed from `pendingCalls`
      and its late output appends as a standalone `(tool output)` block.
- [ ] `finishRun` marks the correct items done after trims have occurred.
- [ ] `go test ./...` and `just test-race` pass.
