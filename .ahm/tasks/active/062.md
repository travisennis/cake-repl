# Fix timeline trim panic when items exceed the cap before first layout

**Code-review finding (2026-07-28).** Reproduced through the real `Update`
path; see Evidence.

## Problem

`appendItem` trims the timeline unconditionally, but maintains the parallel
render cache only when the model is ready (`internal/app/model.go:226-241`):

```go
m.items = append(m.items, it)
if m.cfg.MaxTimelineItems > 0 && len(m.items) > m.cfg.MaxTimelineItems {
    over := len(m.items) - m.cfg.MaxTimelineItems
    m.trimFront(over)
    m.rendered = m.rendered[over:]   // panics: m.rendered is empty when !m.ready
    m.rebuildTimelineContent()
}
if m.ready {
    ...
    m.rendered = append(m.rendered, rendered)
}
```

Before the first `tea.WindowSizeMsg`, `m.ready` is false and `m.rendered` stays
empty while `m.items` grows, so the first append past the cap panics and takes
the REPL down.

The narrow trigger is one symptom of a broader gap: the invariant
`len(m.rendered) == len(m.items)` is only established once `m.ready` is true,
and several paths mutate `m.items` without it. `startNewSession`
(`internal/app/update.go:144-156`) and the `CmdClear` branch
(`internal/app/update.go:290-296`) both clear `m.items` and call
`rebuildTimeline`, which early-returns when not ready
(`internal/app/model.go:320-331`), leaving `m.rendered` stale. `insertItemAt`
has the same shape (`internal/app/model.go:273-280`).

## Evidence

Requires `-max-timeline-items` (or the `max-timeline-items` config key) to be
set, plus enough events before the first `WindowSizeMsg`. Bubble Tea normally
sends the size message early, so this is unlikely in practice — but it is
reachable through the ordinary message path, not just by calling internals:

```
panic: runtime error: slice bounds out of range [1:0]
  app.(*Model).appendItem   internal/app/model.go:231
  app.(*Model).applyEvent   internal/app/update.go:366
  app.Model.Update          internal/app/update.go:51
```

## Fix Direction

Make the render cache a strict function of readiness rather than something the
trim path assumes exists. Either:

- move the whole trim/cache block inside the `m.ready` check (simplest, and
  `rebuildTimeline` already restores everything on the first layout); or
- give `trimFront` ownership of the `m.rendered` trim and have it no-op the
  cache side when not ready.

Prefer whichever leaves one stated invariant in a comment near the `rendered` /
`timelineContent` fields (`internal/app/model.go:76-81`) — note that task 054
is separately correcting the wording of that comment, so coordinate the edit.

Do not change trimming semantics: the oldest items still go first, and
`pendingCalls` indices still shift by `over`.

## Acceptance criteria

- [ ] Appending well past `MaxTimelineItems` before any `WindowSizeMsg` does
      not panic, through the `Update` path.
- [ ] After the first layout, the timeline shows exactly the most recent
      `MaxTimelineItems` entries with correct content.
- [ ] `/clear` and Ctrl+N before first layout leave the cache consistent.
- [ ] `pendingCalls` index adjustment after a trim is unchanged, and a tool
      output whose call was trimmed away still renders as a standalone block.
- [ ] A regression test drives the pre-ready path via `Update`, not by calling
      `appendItem` directly.
