# Consider allowing SGR color sequences through from tool output

Follow-up to task 061 and
[ADR 005](../../../docs/adr/005-untrusted-stream-content-is-sanitized-at-the-ui-render-boundary.md).
**Triage first: this is a product decision, not an obvious fix.**

## Problem

`ui.Sanitize` strips every ANSI escape sequence from stream content, so tool
output renders flat. Colorized output that cake commonly produces — `git diff
--color`, compiler and test-runner diagnostics, `rg`, `eza` — loses the
information its color was carrying.

That is a real usability cost, and unlike the injection risk it applies to
every ordinary session.

## Why it was not done in task 061

The security-relevant sequences are the ones that move the cursor, clear the
screen, write the clipboard (`OSC 52`), or forge hyperlinks (`OSC 8`). SGR
(`CSI ... m`) does none of that: it only sets graphics rendition, and both
`lipgloss.Width` and `ansi.StringWidth` already ignore it, so allowing SGR
through would not reintroduce the padding bug.

The blocker is styling composition, not safety. Every timeline item is rendered
inside a lipgloss style. A stream-embedded reset (`\x1b[0m`, or `CSI 39m` /
`CSI 49m`) terminates the enclosing style mid-block, so the theme's color bleeds
out into the remainder of the frame. Handling that correctly means re-emitting
the enclosing style after every embedded reset — meaningful code and test
surface on the exact path that renders attacker-influenced bytes, which is why
it was kept out of the P1 security fix.

## Relevant Files

- `internal/ui/sanitize.go` — where an allowlist would live.
- `internal/ui/timeline.go` — `renderTool`, the styled block that would need
  reset-aware composition.
- `internal/ui/theme.go` — the enclosing styles.
- `docs/adr/005-untrusted-stream-content-is-sanitized-at-the-ui-render-boundary.md`
  — records the current unconditional decision; changing it needs a new ADR or
  an amendment, not a silent edit.

## Direction If Accepted

1. Parse with the `x/ansi` parser rather than pattern-matching: keep `CSI ... m`
   with validated numeric parameters, drop everything else, including `OSC`,
   `DCS`, `APC`, and all cursor/erase CSI finals.
2. Decide what to do about embedded resets. Either rewrite them to re-emit the
   enclosing style, or normalize them to a style-scoped reset.
3. Bound it: reject SGR parameters outside a known-safe set, so exotic or
   terminal-specific rendition codes do not pass through unexamined.
4. Force-strip under `-no-color` / `termenv.Ascii`, which must stay plain.
5. Consider scoping the allowlist to tool output only, leaving errors,
   warnings, hook text, and the status line unconditionally stripped.
6. Consider whether this should be opt-in via flag or config rather than the
   default, so the safe behavior is what a user gets without asking.

## Decision (2026-08-01)

Opt-in, tool output only, per
[ADR 009](../../../docs/adr/009-opt-in-sgr-passthrough-for-tool-output.md).
New `-tool-color` flag and `tool-color` config key (default `false`). When
enabled, `ui.Sanitize` keeps only `CSI ... m` with validated numeric
parameters, parsed via the `x/ansi` parser; OSC, DCS, APC, and cursor/erase
CSI finals stay stripped; embedded resets re-emit the enclosing lipgloss
style; `-no-color` / `termenv.Ascii` force stripping. Errors, warnings, hook
text, and the status line stay unconditionally stripped.

## Acceptance criteria

- [ ] ADR 009 linked from this task
- [ ] `-tool-color` flag and `tool-color` config key, default `false`
- [ ] SGR (`CSI ... m`) passes through tool output only when enabled
- [ ] OSC, DCS, APC, and all cursor/erase CSI finals remain stripped
- [ ] SGR parameters outside the known-safe set are rejected
- [ ] Embedded resets re-emit the enclosing style (no theme bleed)
- [ ] `-no-color` / `termenv.Ascii` force stripping
- [ ] Default behavior is unchanged from ADR 005
- [ ] The session-and-security guardrail's "no opt-out" failure mode is amended
      to "no implicit opt-out" (per ADR 009)
- [ ] Terminal-injection, width, and padding tests continue to pass
- [ ] README, HelpText, and the CLI guardrail document the flag
- [ ] `just ci` passes

## Comments

**2026-07-30T22:39:52-04:00** — A human product/security decision remains. ADR 005 currently requires unconditional stripping, so Trav must first decide whether colored tool output is valuable enough to change that boundary. If yes, decide default-on versus opt-in, tool-only versus all item kinds, and reset/style-composition semantics, then create an accepted replacement decision before implementation. Acceptance notes must cover a parser-based SGR allowlist, rejection of every non-SGR control family, enclosing-style restoration, `-no-color`, injection regressions, docs, and `just ci`. If the feature is not wanted, cancel it with the rationale linked to ADR 005.
