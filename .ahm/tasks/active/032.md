# Hydrate resumed sessions from cake replay support

## Problem
`cake-repl -resume <uuid>` currently pins the next prompt to an existing cake session, but the TUI starts with an empty local timeline. Users reasonably expect a resumed session window to show prior conversation history before they continue.

Today cake-repl cannot implement that without violating its engine boundary: it must not read cake session files, parse cake's human output, or import cake internals. The missing dependency is a supported cake contract for replaying or exporting a session transcript.

## Blocking Dependency
Blocked until cake ships a stable CLI/API that exposes the prior session transcript in a machine-readable format cake-repl can consume.

Preferred contract:

- `cake --output-format stream-json --replay <uuid>` or equivalent emits replay events for an existing session without running a new prompt.
- The replay stream includes enough information to reconstruct user messages, assistant messages, reasoning summaries when available, tool calls, tool outputs, task boundaries, session id, task ids, and completion metadata.
- Replay output uses the same event schema as live `--output-format stream-json` where possible, or a versioned additive schema that cake-repl can decode forward-compatibly.
- Replay failure modes are explicit: missing session, unreadable/corrupt session, unsupported schema/version, and permission errors should produce structured errors and non-zero exit codes.

Do not implement this by reading `~/.local/share/cake/sessions/*.jsonl` directly from cake-repl.

## Fix Direction
Once cake provides a supported replay/export contract:

1. Add a cake integration path that invokes the replay/export command for the selected resume id before the first prompt runs.
2. Decode replay records through the same event parser when possible. If cake adds replay-specific event types, add them forward-compatibly in `internal/cake/events.go`.
3. Hydrate the timeline during model initialization or early `Init` without marking a live prompt as running.
4. Preserve current session pinning behavior: after hydration, the next submitted prompt still uses `--resume <uuid>`.
5. Show a clear, non-fatal timeline warning when replay fails, then still allow the user to continue with `--resume <uuid>`.
6. Update user-facing docs so `-resume` explicitly says it reloads visible history when cake replay support is available.

## Acceptance Notes
- [ ] Starting `cake-repl -resume <uuid>` hydrates the visible timeline from cake's supported replay/export output before the next prompt is submitted.
- [ ] The next submitted prompt still runs as `cake --output-format stream-json --resume <uuid> -- <prompt>`.
- [ ] Replay does not read cake session files directly from cake-repl.
- [ ] Replay failures are displayed as non-fatal warnings and do not prevent continuing the resumed session.
- [ ] Unknown replay/live event fields remain forward-compatible.
- [ ] Tests cover successful hydration, missing/corrupt session replay failure, and continued prompt execution after hydration.
- [ ] README, help text, and guardrails are updated to reflect the new contract and behavior.
- [ ] Run `just test` at minimum; run `just ci` before handoff for code changes.
