# Show the live context-window size in the status line

## Problem

The status line reports session, next-run mode, model, and cwd, but nothing
about how full the model's context is. Long sessions approach the window limit
silently: the first signal today is cake retrying around an overflow, or the
model degrading.

Requested by Trav (2026-09-22) alongside the terminal-title working/idle
indicator, which shipped as task 084 (`windowTitle`/`titleCmd` in
`internal/app/model.go`).

## What cake exposes today (cake 0.1.0)

Checked against the installed binary and its live streams:

- **`task_complete.usage` is cumulative over the whole task, not the current
  context.** A replayed single-task session reported `input_tokens: 1338566`
  with `input_tokens_details.cached_tokens: 1283200`.
  [`internal/cake/events.go`](../../../internal/cake/events.go) decodes only
  `input_tokens`, `output_tokens`, and `total_tokens`. Input tokens summed over
  many turns cannot be read as "context in use".
- **No per-turn usage reaches stream-json.** Replaying a completed
  `format_version: 4` session emits `session_meta`, `prompt_context`,
  `task_start`, `message`, `reasoning`, `function_call`,
  `function_call_output`, `skill_activated`, `hook_event`, and `task_complete`
  — nothing per turn, and no stream event carries a context figure.
- **cake records the data internally and withholds it from the stream.** cake
  keeps a `turn_usage` session record per provider attempt that reported usage:
  the normalized `usage` (`input_tokens`, `output_tokens`, `total_tokens`, plus
  optional `input_tokens_details.cached_tokens`,
  `output_tokens_details.reasoning_tokens`), with `turn`, optional 1-based
  `attempt`, `usage_presence`, and `terminal_class`. The stream layer drops it on
  purpose: the binary carries the assertion `internal error: entered unreachable
  code: turn_usage records are session-only and have no stream counterpart`, and
  `docs/integrations.md` in the cake repo states that per-attempt detail lives in
  the session file and the telemetry sidecar "so that the machine-readable
  completion document keeps its existing shape". `replay` likewise treats
  `turn_usage` as audit metadata that is neither restored nor re-emitted. The
  context budget itself is computed at run time:
  `log_context_budget()` in cake's `src/clients/agent/agent_loop.rs` logs
  `turn`, `window` (the configured `context_window`) and
  `remaining_context_tokens`, deriving `context_tokens` from the last usage's
  `input_tokens`.
- **The configured window is available per model, unevenly.** `cake debug
  models --json` reports `context_window` as `1000000` for the
  `deepseek-flash-*` entries, `1048576` for `muse-spark`, and `null` for the
  codex, grok, and luna entries.

Reading cake's session files is prohibited by engine isolation, and no current
stream-json field carries the figure, so cake-repl cannot show a real context
number today.

## Options

1. **cake emits per-turn usage on the live stream** (recommended, and chosen by
   Trav on 2026-09-22). Give `turn_usage` a stream-json counterpart carrying the
   attempt's normalized usage, plus the resolved budget (`context_window`, or
   `remaining_context_tokens` as `log_context_budget()` computes it), and
   include it in `replay` output. cake-repl then decodes it forward-compatibly
   and renders a status segment (for example `context: 132k/1M`), showing a bare
   token count when the model's `context_window` is unknown. The record and the
   accounting already exist; the work is the stream schema, a compatibility
   decision, and a cake release. Filed as
   [cake#635](https://github.com/travisennis/cake/issues/635).
2. **cake-repl estimates from the visible timeline** (chars/4). Ships
   immediately with no cake dependency, but the estimate excludes the system
   prompt, the skills catalog, tool schemas, and any timeline entries dropped
   by `-max-timeline-items`, and it ignores cache reads, so it can be wrong by
   multiples. For a number users act on, that is worse than no number.
3. **Poll a new cake introspection command**, e.g. `cake sessions usage --json`
   for the current session, polled after each run. Machine-readable with no
   stream change, but it needs an ADR to widen cake-repl's invocation contract
   (the same blocker as task 011), plus polling and a display that is always one
   turn stale.

## Decision

**Option 1**, chosen by Trav on 2026-09-22: cake streams per-attempt usage and
cake-repl displays it. Options 2 and 3 above are rejected — a chars/4 estimate
from the visible timeline is wrong by multiples, and a polling command would
widen cake-repl's cake invocation contract for a value that is always one turn
stale.

## Blocker

Waiting on [cake#635](https://github.com/travisennis/cake/issues/635): cake must
emit the per-attempt usage record on live stream-json (and in `replay`) before
cake-repl has anything to decode. Nothing in this repository can be implemented
first, and reading cake session files or the telemetry sidecar is prohibited by
engine isolation. Re-accept this task once a cake release carries the record;
update the `What cake exposes today` section with the shipped field names at
that point.

## Acceptance criteria

- A live run's status line shows context usage taken from cake, updated as the
  task progresses, and the value is absent (or explicitly unknown) on streams
  that do not carry it rather than showing a placeholder.
- Decoding stays forward-compatible: a stream without the event, or with extra
  fields, must not break the parser.
- The figure degrades cleanly when the model's configured `context_window` is
  `null`.
- `README.md` and `docs/guardrails/cli-and-user-output.md` describe the status
  segment; `docs/guardrails/cake-integration-and-stream-json.md` records the
  new event's decoding rule.

## Verification

- Parser tests for the new event (present, absent, extra fields) alongside the
  existing `internal/cake/parser_test.go` fixtures.
- Status-line tests in `internal/ui/status_test.go` for the known-window and
  unknown-window renderings.
- A PTY capture of a live run would show the segment change mid-task; see task
  081 for the harness this repository currently lacks.
