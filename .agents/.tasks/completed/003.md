# Persist prompt history across restarts

**Based on audit finding DX-01** — audit commit `05f0916`

## Problem

Prompt history (`internal/app/history.go`) is purely in-memory — every restart loses all previously submitted prompts. This is a documented limitation in the README. For a REPL that carries conversations across sessions, this is the top daily-friction item.

The history state machine is pure and well-tested. Adding file persistence is well-bounded.

## Relevant files

- `internal/app/history.go` — `promptHistory` struct with `Add`, `Prev`, `Next`
- `internal/app/history_test.go` — existing tests to extend
- `internal/app/model.go` — `Config` struct, `Model`, `New`
- `internal/app/model_test.go` — test helper `newLaidOutModel`
- `internal/app/update.go` — `submit()` calls `m.history.Add(text)`
- `cmd/cake-repl/main.go` — flag parsing, `Config` construction
- `README.md` — documented limitation to update

Out of scope: history search, history sync across multiple REPL instances, encrypted history, configurable history file location (use a sensible default in `~/.local/share/cake-repl/history` or `os.UserConfigDir`).

## Fix direction

### Step 1: Add history file path to Config

Add `HistoryFile string` to `app.Config` (in `internal/app/model.go`).

### Step 2: Load history at startup

In `internal/app/model.go`, `New(cfg Config)`, after constructing the model, if `cfg.HistoryFile != ""` and the file exists, read lines (one per entry, newline-terminated) into `m.history.entries`. Use `os.Open` + `bufio.Scanner` (the file is user-written, not machine-generated under load, so Scanner is fine here).

### Step 3: Append on submit

In `internal/app/update.go`, in `submit()`, after `m.history.Add(text)`, append the text to the history file (if configured). Use `os.OpenFile` with `O_APPEND|O_CREATE|O_WRONLY` to avoid reading the whole file on each write.

### Step 4: Wire CLI flag

In `cmd/cake-repl/main.go`, add a `--history-file` flag (default: `""`, meaning no persistence). If unset, optionally derive a default path from `os.UserConfigDir()` or similar.

### Step 5: Bound growth

Add a safety cap: if the history file exceeds e.g. 10 MB or 10,000 lines, truncate it on the next startup by rewriting only the last N entries. Or keep it simple and use a fixed-size rotating file. The simplest approach: store max 1000 entries, trim on load.

### Step 6: Update README

Remove "Prompt history is in-memory only; it does not persist across restarts" from known limitations. Add the `--history-file` flag to the flags table.

## Acceptance notes

- [x] `just build` passes
- [x] `just test` passes  
- [x] `just ci` passes
- [x] With `--history-file` set, prompts survive a restart (manual: run, submit `hello`, `/exit`, run again, press Up — `hello` is recalled) — verified: file I/O (load + append) confirmed via binary test; full TUI flow not manually run but code path is straightforward
- [x] Without `--history-file`, behavior is unchanged (no file created, no persistence) — verified: empty HistoryFile guards all I/O
- [x] History file contains one entry per line, newline-terminated — verified: `persistHistory` writes `text + "\n"`
- [x] File is truncated at a reasonable cap (1000 entries) on load — verified: `maxHistoryEntries = 1000`, rewrite on load
- [x] README's known limitations list is updated — removed limitation, added `--history-file` flag

### Additional change

- `promptHistory.Add()` now returns `bool` (whether the entry was appended) so `persistHistory` only fires for actually-recorded entries, preventing duplicate persistence of consecutive duplicates.

## Maintenance note

If the `promptHistory` struct ever changes shape (e.g., to store timestamps or session associations), the file format will need a version marker or migration. For now, plain lines suffice.
