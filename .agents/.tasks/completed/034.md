# Investigate event ordering in session history

## Problem

During interactive use, events in the session history sometimes appear out of order. Specifically, a command execution event (showing the command being run) appears *after* the text response that references it. This suggests the stream-json event processing may not be preserving the server-sent order, or timeline rendering may be inserting events at the wrong position.

## Investigation scope

1. Verify that the stream-json parser (`internal/cake/events.go`) preserves the order of events as received from `cake`.
2. Check that `internal/app/update.go`'s `applyEvent` applies events to the timeline in receive order.
3. Check if any async processing, batching, or reordering occurs in the runner (`internal/cake/runner.go`).
4. Check if timeline rendering (`internal/ui/timeline.go`) reorders items.

## Relevant files

- `internal/cake/events.go` — event types and parsing
- `internal/cake/parser.go` — NDJSON parsing
- `internal/cake/runner.go` — subprocess management
- `internal/app/update.go` — event application
- `internal/ui/timeline.go` — rendering

## Findings

### Root cause: Cake's Chat Completions backend emits tool calls before text

The event ordering issue originates in cake's `parse_choices` function
(`src/clients/chat_completions.rs`). When the Chat Completions API backend
parses a model response that contains both text content and tool calls, it
pushes `function_call` items to the vector **before** the `message` item:

```rust
// Extract tool calls first
if let Some(tool_calls) = &message.tool_calls {
    for tc in tool_calls {
        items.push(ConversationItem::FunctionCall { ... });
    }
}

// Extract text content (may coexist with tool calls)
if let Some(content) = &message.content && !content.is_empty() {
    items.push(ConversationItem::Message { ... });
}
```

This means the stream-json output from cake for a Chat Completions provider
emits:

```
{"type":"function_call", "name":"bash", ...}
{"type":"message", "role":"assistant", "content":"I'll search for the file."}
```

Instead of the correct order (message first):

```
{"type":"message", "role":"assistant", "content":"I'll search for the file."}
{"type":"function_call", "name":"bash", ...}
```

### cake-repl's side is clean

The investigation confirmed:

1. **Parser** (`internal/cake/parser.go`): Parses lines sequentially in
   receive order. No reordering.
2. **Runner** (`internal/cake/runner.go`): Sends events to a channel in
   stdout order. No batching or reordering.
3. **applyEvent** (`internal/app/update.go`): Applies events in receive
   order by appending timeline items sequentially.
4. **Timeline rendering** (`internal/ui/timeline.go`): Renders items in
   array order with no reordering.

The Responses API backend (`src/clients/responses.rs`) handles ordering
correctly because `parse_output_items` iterates the API's output array in
order, which naturally places text before tool calls.

### Fix applied

Made cake-repl resilient to both orderings by detecting when a `message`
event with `role == "assistant"` arrives while pending tool calls are at
the end of the timeline. In that case, the assistant message is inserted
**before** the first pending tool call rather than appended after it.

This preserves the correct visual order (text before tool call) regardless
of whether cake emits `function_call` before or after `message`.

### Upstream fix needed

The root cause should also be fixed in cake's `parse_choices` by swapping
the order: emit text content before tool calls. The fix is in
`src/clients/chat_completions.rs` in the
[travisennis/cake](https://github.com/travisennis/cake) repository.
