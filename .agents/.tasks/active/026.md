# Cap prompt history during long-lived sessions

## Problem
Prompt history is capped only when loading a persisted history file. During a long-lived REPL session, `promptHistory.Add` keeps appending to memory and `persistHistory` appends each prompt to disk with no cap, so both can grow without bound until the next startup.

## Evidence
- `maxHistoryEntries` is defined in `internal/app/model.go`.
- `loadHistory` trims to the most recent `maxHistoryEntries` and rewrites the file only on startup.
- `promptHistory.Add` in `internal/app/history.go` appends without trimming.
- `persistHistory` in `internal/app/update.go` appends one line per prompt without enforcing the cap.

## Relevant Files
- `internal/app/history.go`
- `internal/app/model.go`
- `internal/app/update.go`
- `internal/app/history_test.go`
- `internal/app/history_io_test.go`

## Fix Direction
Enforce `maxHistoryEntries` at the point history is mutated. Keep the most recent entries and update `idx` after trimming. Keep load-time trimming as a safety net for existing oversized files.

For persisted history, keep the on-disk file bounded after runtime additions. Prefer a small helper that rewrites the configured history file from the in-memory capped history after a new entry is accepted; errors should remain best-effort so a bad history path does not break the REPL.

## Acceptance Notes
- [ ] Adding more than `maxHistoryEntries` prompts in one process leaves `m.history.entries` capped to the most recent entries.
- [ ] A configured history file remains capped during runtime, not only after restart.
- [ ] Consecutive duplicate and empty-entry behavior remains unchanged.
- [ ] Existing oversized history files are still trimmed on load.
- [ ] Focused tests cover in-memory trimming and persisted file trimming.
- [ ] Run `go test ./internal/app` or broader verification.
