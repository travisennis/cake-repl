# Establish ADR supersession tracking conventions

**Based on `docs` audit finding** — `decision_records` scored 2/3 because while two structured ADRs exist, the supersession tracking practice is not yet established. No supersessions are needed today, but the convention should be in place before it's needed under pressure.

## Problem

ADR-001 (session run-mode) and ADR-002 (config file) are accepted and current. Neither has been superseded, so there is no existing pattern for tracking supersession in this repo. When a future ADR supersedes or modifies a previous one, the convention needs to be clear so agents and contributors can trace the decision history.

Without a defined convention, a future author might:
- Edit the old ADR to describe the new decision (rewriting history).
- Create an unlinked new ADR with no reference to what it replaces.
- Omit the supersession relationship entirely, making decision history invisible.

## Relevant Files

### To modify
- `docs/adr/001-*.md` — add a supersession frontmatter field (even if unused yet) as an example.
- `docs/guardrails/documentation.md` — add a note about supersession conventions in the "ADR history" compatibility surface.
- `docs/adr/index.md` (generated by `ahm index`) — ensure supersession status is rendered.

### Read-only context
- `docs/adr/002-*.md` — for format alignment.
- `AGENTS.md` "Docs And ADR Gate" section — where ADR requirements are specified for agents.

## Grooming Finding (2026-07-03)

**`ahm adr supersede <old-id> --by <new-id>` already exists as a built-in command.**

This means the supersession mechanism is already tool-supported in `ahm`. When superseding:
- `ahm adr supersede 009 --by 010` marks ADR-009 as `superseded by ADR-010` and adds a cross-reference to ADR-010.
- No custom frontmatter fields or manual body edits are needed — `ahm` handles the front matter updates.

The task scope reduces to: document this existing command in the documentation guardrail so agents and contributors know to use it rather than manually editing ADR history.

## Fix Direction

### 1. Document `ahm adr supersede` in docs/guardrails/documentation.md

In the "ADR history" compatibility surface block, add:

```markdown
- **Supersession.** When a new ADR supersedes or replaces a previous decision,
  use `ahm adr supersede <old-id> --by <new-id>` instead of editing the old
  ADR by hand. The command marks the old ADR as superseded, adds a
  cross-reference, and regenerates the ADR index.
```

Remove the frontmatter-field approach described in the original task — `ahm` manages it mechanically.

### 2. Verify the supersede command's output matches expectations

```bash
# Dry-run to confirm the command is available and produces sensible output
ahm --dry-run adr supersede 001 --by 002
```

(Expected: tool updates ADR-001 frontmatter and adds cross-reference note. Dry-run should show the planned changes without executing.)

### 3. Remove supersession field definition from Fix Direction

The original task proposed adding `supersedes`/`superseded-by` frontmatter fields manually. Since `ahm` handles this, no front matter changes are needed in ADR files. The existing ADRs are unmodified.

### Acceptance criteria

- [ ] `ahm adr supersede --dry-run 001 --by 002` completes without error (verifying the tool handles supersession).
- [ ] `docs/guardrails/documentation.md` documents the `ahm adr supersede` command as the canonical supersession mechanism, with usage example.
- [ ] The "ADR history" section in the documentation guardrail includes a supersession bullet referencing `ahm adr supersede`.
- [ ] No existing ADRs are modified — the task is documentation-only.

## Constraints

- Do not modify existing ADRs — the task is to document the `ahm adr supersede` command, not to apply supersessions.
- Supersession is opt-in — not every new ADR needs supersession, only those that replace or modify a previous decision.
- The convention delegates the mechanical work to `ahm` — no custom frontmatter fields or manual body edits.
